     [spend, reach, impressions, meta_form_leads, cost_per_lead, ctr,
     link_clicks, cpc_link_click], length 8, no nulls, no cpc_all,
     cost_per_lead = "$5.60" ($140 spend / 25 leads), not a dash.

  2. "wizard's own untouched default selection (defaultMetaSelection,
     never edited by the user...) -> the same 8 keys still reach the
     slide, still no dash" — calls the REAL defaultMetaSelection()
     function (the same one the /metrics route uses to pre-fill Step 4)
     with headers matching the same CSV, asserts it produces the exact
     same 8 keys, then feeds that as campaignMetricOverrides and asserts
     the same clean result.

     campaignMetricOverrides at all, only the selectedMetrics union")

=== FILES NAMED IN THE REQUEST BUT DELIBERATELY LEFT UNCHANGED ===

src/components/report-upload-wizard.tsx (originally Fix 1)
  Verified there is no metricsTouched gate anywhere in the current file.
  currentSelectedMetricsPayload()/currentCampaignMetricOverridesPayload()
  are gated only on `perCampaignMetrics.size === 0`, and
  fetchObjectivesAndMetrics() already populates perCampaignMetrics
  automatically on Step 2's Continue click (handleCampaignsContinue) —
  before the user can ever reach Step 4 — regardless of whether Step 4
  is later visited or edited. The only way campaignMetricOverrides stays
  undefined at generate time is if that /metrics fetch genuinely fails
  (network/server error), which is documented, intentional, sensible
  fallback behavior (falls through to the engine's fully-automatic
  per-objective assignment rather than stranding the wizard) — not a bug
  to remove. No change made; verified via the new "untouched default
  selection" test above, which calls the real code path this concern
  was about.

src/lib/nre/available-metrics.ts (originally Fix 2)
  objectiveMetricKeys('META FORM LEADS').costKey does compute the plural
  "cost_per_meta_form_leads" — confirmed, unchanged from prior rounds'
  findings. Did NOT change it to match the wizard's real singular key,
  because a slot-assignment.test.ts comment explicitly documents this as
  intentional: the synthetic key only needs to agree with what
  buildMultiObjectiveSelection (the mixed-objective account-wide
  selection) itself derived when building that pair, never the real
  dictionary column key — the two are allowed to differ by design, and
  several existing tests assert the plural form directly. Changing
  objectiveMetricKeys would risk breaking that separate, working system.
  The actual practical gap (cost_per_lead resolving to a dash) was
  already fixed in round 2109fc1 via a scoped baseline alias in
  report-data.ts, confirmed still working by the new required test.

src/lib/nre/meta-dictionary.ts (originally Fix 3)
  cost_per_lead's perUnitOf: "website_leads" is unchanged — confirmed
  correct as-is for the OTHER objectives (leads/website_leads) this same
  selectable key also applies to. The META FORM LEADS-specific gap was
  already fixed in round 2109fc1 (report-data.ts baseline alias:
  baselineValues["cost_per_lead"] = baseline.cprValue, scoped to
  objectiveKeyFor === "meta_form_leads" only) rather than changing this
  shared dictionary entry, which would have reintroduced the exact cross-
  contamination risk avoided back then (a WEBSITE LEADS campaign that
  manually adds "COST PER LEAD" would get the wrong value). Confirmed
  still working by the new required test (cost_per_lead = "$5.60", not
  dash).

src/lib/nre/slot-assignment.ts (originally Fix 4)
  No cpc_link_click -> cpc_all substitution mechanism was ever found in
  this file across the last several rounds' tracing (aggregateDynamicMetrics
  keys its result strictly by metric.key; lookupMetricValue is called
  with one metric at a time; redistributeCardSlots only ever drops a
  slot whose value is null, never swaps a real value for a different
  key). This is now doubly moot: Fix 5 means redistributeCardSlots isn't
  called for the wizard-selection path at all anymore, so there is no
  redistribution logic in that path capable of dropping or substituting
  anything. Confirmed via the new required test: cpc_link_click resolves
  to "$0.85" and "cpc_all" never appears in the output. No change made —
  the function's own extraCostKeys/extraResultKeys fix from round
  7295461 is left in place, untouched, still correct and still tested in
  isolation, simply unused by the pipeline now.
