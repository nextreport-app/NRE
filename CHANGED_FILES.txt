CHANGED_FILES.txt — commit 2109fc1 "Fix cost_per_lead resolving to a dash for META FORM LEADS wizard selections"

src/lib/nre/report-data.ts
  computeMetaSlideMetrics(): added a 4-line objective-conditional alias
  right after the existing resultKey/costKey aliasing block:

    if (objectiveKeyFor(campaignObjective.resultLabel) === "meta_form_leads") {
      baselineValues["cost_per_lead"] = baseline.cprValue;
    }

  So when this specific campaign's SelectedMetric list contains the
  literal key "cost_per_lead" (as produced by available-metrics.ts's
  defaultMetaSelection when the CSV has a "Cost per lead" column instead
  of "Cost per on-facebook lead"), buildSlotsFromSelection's baseline
  lookup now finds a value there instead of falling through to raw-row
  aggregation.

ROOT CAUSE (traced through the actual aggregation code, not the
originally proposed diagnosis): "cost_per_lead"'s dictionary entry
(meta-dictionary.ts:293-296) has perUnitOf: "website_leads" —
aggregateDynamicMetrics (dynamic-metrics.ts) computes it as
sum(spend) / sum(website_leads column). A META FORM LEADS campaign's CSV
rows have no website_leads data at all (a different objective's column),
so the denominator is 0, the aggregate is NaN, and lookupMetricValue
renders NaN as "—". That dictionary entry is correct as written for the
OTHER objectives (leads/website_leads) it's also selectable for — the
bug is that "cost_per_lead" reaches this raw-aggregation path at all,
because its key doesn't match objectiveMetricKeys' own costKey for META
FORM LEADS ("cost_per_meta_form_leads", PLURAL, mechanically slugified
from the resultLabel) — never the literal "cost_per_lead" key
available-metrics.ts's defaultMetaSelection actually uses in its
"CSV has a 'Cost per lead' column" branch.

WHY THIS FIX LIVES IN report-data.ts, NOT slot-assignment.ts (as
originally proposed): buildSlotsFromSelection has no campaignObjective
parameter — it's shared/objective-agnostic, used for every objective and
both slide 1 and slide 2. An unconditional "cost_per_lead falls back to
cost_per_result" rule placed there would also fire for a WEBSITE LEADS
campaign that manually adds "COST PER LEAD" via the Metric Cards "Add
from your CSV" pool — where perUnitOf: "website_leads" is CORRECT and
this fallback would silently show the wrong number instead of the real
one. report-data.ts's computeMetaSlideMetrics already has
campaignObjective in scope at exactly the point this needs to be
conditional (two lines above, for the identical resultKey/costKey
aliasing reason), so the fix extends that existing mechanism instead of
adding an unconditional special case somewhere that structurally can't
scope it correctly.
